## 1. 参与项目情况报告

### 1.1 项目基本情况

本项目"模拟面试智能体系统"是一款基于多模态 AI 技术的智能化模拟面试平台，旨在解决传统面试准备中缺乏真实环境模拟、难以自我察觉肢体/表情问题、缺少个性化量化反馈等核心痛点。

**项目技术架构**：

- **后端框架**：Python 3.9+、FastAPI、SQLAlchemy
- **数据库**：MySQL 8.0+
- **AI 技术栈**：MediaPipe（姿态分析）、DeepFace（情绪识别）、Whisper（语音识别）、阿里云百炼 Qwen3.5-plus / 讯飞星火（大语言模型）
- **前端框架**：Vue.js
- **通信方式**：HTTP REST API + WebSocket + WebRTC
- **项目规模**：团队 6 人，开发周期 12 周，预算约 500 元

**系统核心功能**：

1. 用户管理体系（注册、登录、个人信息管理、JWT 鉴权）
2. 智能面试系统（实时视频面试、自适应 AI 提问、多轮对话）
3. AI 多模态分析（肢体动作识别、眼神接触检测、情绪状态分析、语音流畅度评估）
4. 智能评测报告生成（多维度雷达图评分、结构化综合评语、个性化改进建议）
5. 历史记录管理与复盘回放
6. AI 助手与社区论坛

**项目整体进度**：项目按 12 周计划有序推进，经历了项目立项（W1-W2）、系统设计（W3-W4）、基础开发（W5-W8）、核心功能开发与集成（W9-W10）、全链路联调与交付（W11-W12）五个阶段，最终顺利完成了全部预定功能的开发与交付。

### 1.3 项目实施过程中遇到的问题及处理结果

#### 问题一：需求边界模糊，功能描述与接口设计存在重复交叉

- **问题描述**：在需求分析初期（W3-W4），SRS 文档中"内部接口需求"与"外部接口需求"的边界不够清晰，功能描述与接口设计之间存在多处重复交叉，导致文档结构混乱、可读性差。
- **处理过程**：在 W4 的需求汇报中认真听取了老师的评审意见后，对 SRS 文档进行了系统性重构——明确了内部接口（模块间调用）与外部接口（前后端 API）的边界，新增了"人机交互 UI 接口需求"章节，同时优化了需求层次结构，将接口细节统一收归到接口需求章节。
- **处理结果**：重构后的 SRS 文档逻辑清晰、层次分明，功能需求与接口定义之间不再重复，为后续的 SDD 编写和代码开发提供了准确、统一的需求基线。

#### 问题二：软件设计文档（SDD）初稿结构混乱、内容不全面

- **问题描述**：在 W5 完成的 SDD 初稿存在章节结构混乱（模块划分逻辑不清）、内容缺失（部分核心模块缺少详细设计说明）、图表化表达不足（复杂交互流程缺乏时序图和状态转换图）三大问题。
- **处理过程**：针对导师评审指出的问题，在 W6 进行了第一轮深度修订——严格按照软件设计文档规范重构了章节逻辑，补充了核心模块的详细设计说明；在 W7 结合课堂汇报反馈进行第二轮终版修订——细化了 AI 分析引擎层设计，增加了视频帧分发器与多模态分析模块的并行协作流程图，补全了全部 15+ API 端点的请求/响应 Schema 定义。
- **处理结果**：经过两轮修订后，SDD 达到了专业级的文档标准，能够为后端开发提供精确的技术指导，确保了开发过程中的接口一致性和架构完整性。

#### 问题三：大模型 API 响应延迟影响用户体验

- **问题描述**：W10 开发报告生成功能时发现，在生成千字深度评测报告时，大模型的文本生成耗时约 15\~20 秒，虽满足详细设计中 ≤30 秒的指标，但同步等待容易引发前端网关超时（Gateway Timeout），影响用户体验。
- **处理过程**：提出了异步报告生成机制的优化方案——WebSocket 面试结束后立即返回"评测生成中"状态，后端将报告生成逻辑放入异步任务队列处理，完成后通过消息通知前端刷新获取结果；同时优化了 Prompt 设计，采用分段式生成策略（先产出结构化评分数据，再基于数据生成评语文案），降低了单次 API 调用的复杂度。
- **处理结果**：通过异步化处理后，用户不再需要长时间等待，体验明显改善；分段式 Prompt 策略也使生成报告的质量更加稳定可控。

#### 问题四：视觉分析延迟与暗光环境识别精度不足

- **问题描述**：W9 集成 AI 引擎后发现，前端收到的实时情绪反馈存在约 1.5 秒的累积延迟；在暗光或复杂背景下，MediaPipe 姿态检测的准确率明显下降，出现了误判。
- **处理过程**：在 W11 的全链路联调中，正式上线了"跳帧检测"策略——对坐姿和环境指标每 5 帧检测一次，优先保障眼神对视等核心指标的实时性；同时在 AI 路由层嵌入了直方图均衡化等对比度增强预处理算法。
- **处理结果**：跳帧策略成功将前端实时反馈延迟压降至 450ms 以内，达到了 WebSocket 延迟 ≤ 500ms 的设计要求；对比度增强算法有效改善了暗光环境下的识别精度，误判率显著降低。

#### 问题五：安全漏洞——历史报告查询接口存在横向越权风险

- **问题描述**：W11 全链路联调测试中发现，`/api/interview/reports/history/{accountID}` 接口在普通用户修改 URL 中的 accountID 参数后，可以越权查看其他人的面试报告。
- **处理过程**：立即将此问题列为最高优先级修复项，在 FastAPI 的依赖项（Depends）中添加了严格的 JWT 鉴权校验逻辑，验证当前请求 Token 中的 accountID 是否与路径参数一致，对不一致的请求直接返回 403 Forbidden。
- **处理结果**：漏洞被完全修复，确保了用户数据的隐私安全。同时将此案例记录为团队安全规范的一部分，提醒全体成员在后续开发中注意接口权限校验。

#### 问题六：前后端接口对接进度不一致

- **问题描述**：W5-W6 阶段，前端的 UI 原型完成后因后端接口尚未就绪无法进行联通性测试，前后端存在开发节奏不匹配的问题。
- **处理过程**：作为 PM，协调团队采用"接口文档先行 + Mock 数据并行开发"的策略——后端优先输出 Apifox 中定义的接口规范文档交付前端，前端基于 Mock 数据先行完成 UI 交互逻辑；后端同步推进核心接口开发，在 W8 完成了 15+ 接口的初步跑通后立即启动联通性测试。
- **处理结果**：通过 Mock 数据并行开发模式，前后端得以高效并行推进，避免了相互等待的时间损耗，最终在 W11 顺利完成全功能联调。

### 1.4 参与项目过程的体会与项目评价

#### 1.4.1 项目管理层面的体会

担任项目负责人让我深刻体会到，软件项目管理不仅仅是安排任务和跟踪进度，更需要在以下几个方面做好平衡：

1. **需求与时间的平衡**：项目初期我们花了大量时间打磨需求文档（W1-W4 占总周期 1/3），这一决策在后期开发中得到了验证——清晰的需求基线使得开发团队少走了很多弯路，减少了返工成本。好的需求分析是项目成功的一半。
2. **文档与代码的关系**：通过本项目我认识到，系统设计文档（SDD）并非束缚开发的"繁文缛节"，而是保障团队协作一致性的"施工蓝图"。当 SDD 中的接口定义、数据流转、模块交互被准确描述后，6 人团队在并行开发时能够始终保持接口一致性和架构完整性。
3. **沟通机制的重要性**：每周站会和代码审查机制的坚持执行，使问题能够被及时发现和暴露。例如 W11 的安全漏洞就是在联调测试中通过主动排查发现的，如果缺乏有效的沟通机制，这类问题很可能被遗漏到交付阶段。

#### 1.4.2 技术实践层面的体会

1. **大模型集成的"工程化"挑战**：在本项目中，大模型的调用本身并不复杂（OpenAI 兼容接口几行代码即可完成），但真正有挑战的是如何将其"工程化"——包括 Prompt 的精心设计、输出格式的约束与解析、异步调用的超时处理、备选模型的容灾方案等。这些工程化考量直接影响着系统的稳定性和用户体验。
2. **多模态融合的价值与难点**：将计算机视觉（姿态、表情、眼神）与自然语言处理（ASR 转录、LLM 分析）进行有效融合，是系统的核心竞争力所在。实践中发现，不同模块的输出格式、时间粒度、置信度差异很大，聚合算法需要充分考虑这些差异，才能产出客观准确的综合评分。
3. **性能优化没有"银弹"**：W9 的 1.5 秒延迟问题，最终通过"跳帧检测"策略而非增加算力来解决，说明性能优化很多时候不在于使用更强的硬件，而在于找到正确的优化方向——优先保障核心指标的实时性，对非核心指标适当降频。

#### 1.4.3 团队协作层面的体会

1. **分工明确的团队效率最高**：从项目一开始就明确了 6 人各自的核心职责（前端 2 人 + 后端 3 个方向 + PM），避免了大锅饭式的模糊分工。每个人在自己的专业方向上深耕，整体效率远超模糊分工的团队。
2. **文档是团队协作的"通用语言"**：在 6 人并行开发的场景下，接口文档（Apifox）和设计文档（SDD/详细设计）起到了"契约"的作用——前端不需要关心后端如何实现 AI 分析，只需要按照接口规范获取数据；后端也不需要关心前端如何渲染雷达图，只需要按时交付约定的 JSON Schema。

#### 1.4.4 个人成长与收获

1. **全流程项目管理能力的提升**：这是第一次以 PM 身份完整经历了一个软件项目从立项、需求、设计、开发、测试到交付的全生命周期，对软件工程的各个阶段有了真实的体感认知，不再只是课本上的理论。

#### 1.4.5 对项目的总体评价

本项目在技术架构上实现了 FastAPI + WebSocket + 多模态 AI 的深度整合，功能上覆盖了从用户注册、视频面试、AI 分析到评测报告生成的完整闭环，具有较高的技术含量和实际应用价值。

**项目亮点**：

- 架构设计合理，前后端分离 + 分层架构使系统具备良好的可维护性和扩展性
- AI 分析维度全面（肢体、眼神、情绪、语音 4 大类 7 小维度），评测结果具有较高参考价值
- 文档体系完整规范（SRS → SDD → 详细设计 → 接口文档），可作为后续类似项目的参考模板

**存在的不足与改进方向**：

- 高并发场景下的性能优化仍需加强（多路视频同时接入时 CPU 负载偏高）
- 大模型 API 成本控制和调用频率管理尚未建立完整的限流机制
- 系统的自动化测试覆盖不足（目前主要依赖手动联调测试）
- 视觉分析在极端环境（强光、多人、复杂背景）下的鲁棒性有待进一步提升

**总体而言**，本项目在有限的时间（12 周）和预算（500 元）条件下，成功交付了一个功能完整、架构清晰、技术先进的模拟面试智能体系统。作为项目负责人，我为自己和团队在这 12 周中的付出与成果感到自豪。
